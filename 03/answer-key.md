## 2 Q1 Одна агрегация вместо повторных подзапросов

Решение: [self-check/01.sql](self-check/01.sql). Один раз отбираем оплаченные заказы и группируем по customer_id; присоединяем к customers через LEFT JOIN. COALESCE нужен обоим полям метрик. Это сохраняет клиентов без оплаченных заказов.

Исходный план содержит два SubPlan. Внутри каждого Seq Scan по orders имеет loops=1 200. Средняя выдача скана — 27,25 строки, но он каждый раз проверяет 48 000. Всего два подзапроса делают около 115,2 млн проверок. Родительский план сообщает shared hit=960 009; 480 000 hit каждой ветки уже включают все её loops и не умножаются ещё раз.

Новый план читает orders один раз, выдаёт 32 696 оплаченных заказов и агрегирует до 1 156 клиентов с оплатами. Hash Left Join сохраняет все 1 200 клиентов. Общие shared hit=409, из них 400 относятся к одному проходу orders. Пустые метрики есть не только у 12 клиентов без заказов: 32 клиента имеют только pending-заказы. У всех 44 результат — два нуля.

Вывод: выигрыш объясняется удалением повторных проходов, а не магическим свойством JOIN. При ограничении одним клиентом стоимость массовой агрегации может стать лишней; это отдельный эксперимент.

## 3 Q2 Полусоединения вместо комбинаций

Решение: [self-check/02.sql](self-check/02.sql). Каждый EXISTS выражает независимое наличие строки: подходящая позиция, успешная оплата, email. Выдаются только колонки orders, а число дочерних совпадений не нужно.

Исходные JOIN выдают 82 438 строк на вход HashAggregate, который реализует DISTINCT и оставляет 20 346 заказов. Новый план содержит три Hash Right Semi Join. Они сохраняют одну строку заказа после проверки условия; итог тоже 20 346. Промежуточные результаты уменьшаются, завершающая агрегация DISTINCT исчезает.

На этом стенде сохраняются проходы по четырём таблицам. Поэтому медиана улучшилась примерно в 1,18 раза, хотя структурное сокращение ясно видно. EXISTS не гарантирует раннее прекращение **всего** скана дочерней таблицы: выбранный хеш-план может читать её целиком.

Эквивалентность опирается на независимость проверок и уникальность orders.id. Если нужно вернуть отдельные платежи, посчитать письма или сопоставить поля двух дочерних строк между собой, этот контракт уже другой. Просто убрать DISTINCT из исходника было бы ошибкой.

## 4 Q3 Убрать широкую материализацию

Решение: [self-check/03.sql](self-check/03.sql). Прямой SELECT нужных полей с фильтром по типу и временному диапазону. Можно сохранить CTE, если его форма разрешает встраивание и план подтверждает устранение лишнего хранения.

Исходный CTE читает 380 608 строк шириной estimated width=289. CTE Scan отбрасывает 379 022 и выдаёт 1 586. Подробный план показывает Storage: Disk, Maximum Storage=112 248 kB, temp written=14 031 блок. Это отдельное промежуточное состояние, которое не нужно выдаче из трёх колонок.

Новый Seq Scan также читает исходную events и отбрасывает те же 379 022 строки, но нет CTE Scan и временной записи. Суммарные shared hit+read в обоих вариантах соответствуют одному проходу по 15 225 блокам events; соотношение hit/read меняется из-за кеша. Снижение temp и стоимости хранения объясняет ускорение при сохранившемся скане.

Не делайте вывод, что любой WITH медленный. MATERIALIZED полезен, когда один дорогой результат действительно нужно повторно использовать. На этом запросе потребитель один и нужен узкий отфильтрованный набор.

## 5 Q4 Агрегировать позиции выбранных заказов

Решение: [self-check/04.sql](self-check/04.sql). Отбираем заказы по тем же status и границам, LEFT JOIN присоединяем позиции и группируем по идентификатору заказа и клиента.

До переписывания HashAggregate получает все 142 518 позиций и выдаёт 47 506 групп. Memory Usage в подробном плане — 7 441 kB; Batches=1. Это возможно при work_mem=4MB, потому что лимит хеша учитывает hash_mem_multiplier=2. Нельзя утверждать, что при 4MB каждый узел обязан уложиться ровно в четыре мегабайта.

После переписывания Hash Right Join оставляет 1 625 строк для агрегации, итог — 545 заказов; Memory Usage=161 kB. Среди них пять заказов без позиций. Они дают по одной расширенной NULL строке после LEFT JOIN: count(i.id)=0, COALESCE(sum(...),0)=0. COUNT(*) дал бы неверную единицу.

Оба варианта читают те же orders и order_items, общие shared hit=1 448. Ускорение примерно в 2,9 раза возникает за счёт меньшего входа и состояния агрегации. Замена item_total на total_cents нарушила бы условие: на стенде у непустого заказа сумма позиций — 6 000, а сумма заказа другая.

## 6 Q5 Уменьшить вход ранжирования

Решение: [self-check/05.sql](self-check/05.sql). Сначала оставляем нужные заказы и их события, затем DISTINCT ON выбирает одну строку по occurred_at DESC и id DESC.

Исходный Sort получает 380 608 строк. Метод — external merge, Disk=14 640 kB, temp read=1 830, written=1 836 блоков. WindowAgg имеет Run Condition row_number<=1 и отдаёт 47 576 первых событий, однако дочерний Sort всё равно обрабатывает полную историю. Только после этого JOIN с нужными orders оставляет 541 строку.

Новый Hash Join читает events и orders, но отдаёт сортировке только 4 328 событий выбранных заказов. Sort использует quicksort, Memory=395 kB, temp отсутствует. Unique выбирает 541 победителя. Из 545 оплаченных заказов интервала у четырёх нет событий; по условию они отсутствуют в обоих результатах.

Перенос сохраняет целые группы order_id, не меняя состав событий внутри них. id DESC обязателен при совпадении времени: у каждого непустого заказа последние два события имеют одинаковый occurred_at. Перенос event_type='email' внутрь ранжируемого набора выбирал бы последнее email вместо последнего события вообще.

Допустимое альтернативное решение — оставить row_number над теми же 4 328 событиями. Проверять нужно вход Sort/WindowAgg: именно сокращение входа даёт основной эффект. «DISTINCT ON всегда быстрее оконной функции» из этого опыта не следует.

## 7 Контрпримеры и контроль смысла

[diagnostics.sql](diagnostics.sql) содержит короткие опыты, которые можно выполнить после самостоятельной работы:

```sh
docker compose exec -T postgres psql -X -U course -d course_hw03 -v ON_ERROR_STOP=1 -f /work/settings.sql -f /work/diagnostics.sql
```

- NOT IN возвращает 0 заказов без успешной оплаты из-за NULL в подзапросе. NOT EXISTS возвращает правильный ненулевой набор. Это разные формы по семантике.
- Заказ 97 без позиций: COUNT(*)=1, COUNT(i.id)=0, SUM без COALESCE=NULL.
- Заказ 7: три позиции и два успешных платежа дают шесть комбинаций. Сумма позиций через оба JOIN — 12 000, отдельно — 6 000. DISTINCT суммы не является общим исправлением.
- Последние события заказа 7 — id 56 и 55 с одинаковым временем; победитель при id DESC — 56.
- `(1,1) EXCEPT (1)` пуст, а EXCEPT ALL содержит одну строку: обычный EXCEPT не доказывает равенство кратностей.

Для типов колонок учтите: SUM(bigint) возвращает numeric, COUNT — bigint. В Q4 новая форма сохраняет numeric для item_total и bigint для item_count. Если добавили касты, проверьте метаданные и объясните, почему они допустимы; одинаковый вывод EXCEPT ALL не доказывает одинаковый тип API.

«В Q4 сканы остались полными: обе версии обратились к 1 448 буферам. Изменился вход агрегации: вместо 142 518 позиций и 47 506 групп обрабатывается 1 625 соединённых строк и 545 групп. Заказы без позиций сохраняются через LEFT JOIN, число считается по i.id. Обе EXCEPT ALL пусты; медиана при одинаковой памяти снизилась с 27,621 до 9,530 мс. На другой выборке эффект зависит от доли нужных заказов».

Такой ответ связывает контракт, изменение структуры, корректность и измерение. Полный план и все измерения сохраняются вместе с SQL. Если конкретная версия PostgreSQL выбрала другой допустимый узел, разбор оценивается по реальной работе, а не по совпадению названия узла с этим ключом.

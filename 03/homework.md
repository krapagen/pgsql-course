# Домашнее задание 3 Оптимизация пяти запросов без индексов

Вы расследуете медленные отчёты сервиса заказов. Для каждого из пяти запросов нужно сохранить результат, убрать конкретную лишнюю работу и показать изменение по планам и измерениям. На стенде готовые схема и данные, а индексов нет совсем. Ожидаемое время основной работы — 2,5–3,5 часа; дополнительные эксперименты — ещё 30–60 минут.

Исходное задание курса: оптимизировать пять плохих запросов переписыванием, приложить исходный и новый SQL, планы до/после и короткое объяснение эффекта. Данные, ограничения эксперимента, протокол и критерии ниже — методическая разработка этого задания.

## 1 Подготовить стенд

Скопируйте папку пакета и откройте терминал в ней, рядом с compose.yaml. Для основной работы нужен Docker с Compose; psql уже находится в контейнере. Автоматические проверки через Python 3 доступны по желанию и используют только стандартную библиотеку.

```sh
docker compose up -d --wait
docker compose exec -T postgres psql -X -U course -d course_hw03 -v ON_ERROR_STOP=1 -f /work/schema.sql -f /work/seed.sql -f /work/settings.sql -f /work/sanity.sql
```

Схему и seed применяйте один раз в пустой базе. Ожидаемые строки: customers 1 200, orders 48 000, order_items 142 518, payments 96 001, events 380 608. Запрос к pg_indexes должен вернуть пустую выдачу. Есть 12 клиентов без заказов, 494 заказа без позиций и 424 заказа без событий. Последний платёж имеет NULL order_id.

Все пять таблиц находятся в схеме lab. Идентификаторы уникальны в готовых данных и проверяются sanity.sql; PK/FK намеренно опущены, чтобы даже автоматически создаваемых индексов не было. Это особенность эксперимента, а не образец проектирования прикладной схемы.

## 2 Соблюдать условия сравнения

- Меняйте только SELECT/WITH ... SELECT. Не меняйте данные, таблицы, ограничения, статистики, индексы или серверные настройки ради ускорения.
- Сравнивайте пару на одном наборе данных и при одинаковых настройках из settings.sql: work_mem=4MB, jit=off, max_parallel_workers_per_gather=0, UTC. Отключение JIT и параллелизма здесь упрощает сравнение и не является оптимизацией решения.
- Сохраняйте колонки, их порядок, значения и кратности. Имена и типы тоже должны соответствовать контракту. Нулевой COUNT, NULL и отсутствие строки различайте явно.
- Q1–Q4 не обещают порядок выдачи. Q5 требует одинакового выбора последней строки каждой группы; порядок всех заказов не входит в контракт.
- Не подменяйте SQL-работу кешем приложения, временной таблицей, материализованным представлением или заранее рассчитанными ответами.

Откройте [README](README.md), если нужны повторный запуск или отдельное psql-подключение. Команды проверки ниже выполняют SELECT в READ ONLY транзакции и не создают объектов.

## 3 Разобрать пять запросов

Пять исходных запросов и места для ответов находятся в [queries.sql](queries.sql). Прочитайте запрос и его контракт **до** просмотра плана. Запишите новый SELECT рядом с исходным в соответствующем блоке. Для замеров выполняйте отдельный запрос. Если выберете автоматическую проверку, перенесите решения в solutions/01.sql ... solutions/05.sql: по одному SELECT или WITH ... SELECT с завершающей точкой с запятой на файл. Отдельные копии исходников лежат в bad/.

### Q1 Метрики каждого клиента

Результат: customer_id, paid_count, paid_total. Все клиенты остаются, включая клиентов без оплаченных заказов: у них два нуля. Суммируется orders.total_cents только для status='paid'.

Расследуйте число исполнений подзапросов и объём проверенных ими строк. Убедитесь, что две метрики не требуют двух полных проходов для каждого клиента. Объясните, что происходит с SUM и COUNT при отсутствии оплаченных заказов, и почему выбранный тип соединения сохраняет контракт.

### Q2 Наличие трёх дочерних условий

Результат: уникальные пары order_id, customer_id для оплаченных заказов. У заказа должны существовать хотя бы одна позиция sku_id <= 50, хотя бы один успешный платёж и хотя бы одно email-событие. Их количество не нужно возвращать.

Найдите, где возникает размножение строк, и оцените его на одном заказе с несколькими подходящими строками в каждой таблице. Уберите лишние комбинации, сохранив три независимые проверки. Объясните, почему простого удаления DISTINCT недостаточно.

### Q3 Узкая выдача событий за два дня

Результат: event_id, order_id, occurred_at для email-событий в интервале `[2026-04-29 00:00, 2026-05-01 00:00)`. payload не нужен.

Найдите границу, из-за которой сохраняется вся широкая история. Сопоставьте shared buffers и temp до/после. Объясните, какая работа остаётся неизбежной без индекса и почему одинаковый скан исходной таблицы совместим с ускорением.

### Q4 Метрики позиций нужных заказов

Результат: order_id, customer_id, item_total, item_count для оплаченных заказов с created_at в том же интервале. item_total — сумма qty × price_cents; item_count — количество позиций. Заказ без позиций должен остаться с нулями. orders.total_cents не является заменой item_total.

Проверьте объём агрегации до соединения с нужными заказами. Уменьшите число обрабатываемых групп. Объясните, почему после LEFT JOIN нельзя автоматически использовать COUNT(*) и как вы избегаете размножения сумм.

### Q5 Последнее событие выбранных заказов

Результат: order_id, event_id, event_type, occurred_at для оплаченных заказов с created_at в том же интервале, имеющих события. Для каждого заказа выбирается ровно одна строка по `occurred_at DESC, id DESC`. Заказ без событий не возвращается.

Исследуйте вход Sort и WindowAgg. Попробуйте ограничить нужные группы раньше; менять оконную функцию необязательно. Докажите выбор победителя при одинаковом occurred_at. Объясните, почему фильтр по order_id до ранжирования здесь допустим, а фильтр по event_type мог бы изменить смысл.

## 4 Проверить равенство результатов

Для каждой пары заполните [comparison.sql](comparison.sql): исходный SELECT в before_result, новый — в after_result, без завершающих ';' внутри CTE. В заготовке приведена Q4 и пустой after_result; до замены его вашим решением проверка должна показать расхождение.

В psql выполните `\i /work/comparison.sql`. before_minus_after и after_minus_before должны быть 0. Сравнение выполняется одним SQL-оператором, поэтому обе выдачи используют один снимок данных. EXCEPT ALL проверяет значения и кратности; имена, порядок и типы колонок проверьте отдельно: введите каждый SELECT без завершающей ';', а на следующей строке выполните `\gdesc`.

Совпадение только COUNT(*) не является проверкой. Объяснение должно дополнительно покрывать пограничные случаи из условий задач. Не исправляйте расхождение удалением данных из стенда. **План обёртки сравнения нельзя использовать как план оптимизируемого запроса**.

По желанию после заполнения файлов solutions/ выполните из терминала компьютера:

```sh
python3 tools/check.py --solutions solutions
```

Скрипт выполняет обе версии каждой задачи одним SQL-оператором и сравнивает результаты через EXCEPT ALL в обе стороны. Для каждой пары before_minus_after и after_minus_before должны быть 0. Затем через psql `\gdesc` он сравнивает имена, порядок и типы колонок: columns_equal должен быть true. Проверка относится к готовым данным; порядок строк и корректность на других данных требуют отдельного рассуждения.

## 5 Измерить до и после

Откройте psql, выполните `\i /work/settings.sql` и поставьте `EXPLAIN (ANALYZE, BUFFERS, SETTINGS, TIMING OFF)` перед текстом выбранного запроса из queries.sql. Сделайте по одному прогреву, затем по три запуска каждой версии, меняя порядок. Сохраните полный вывод до и после; для удобства можно направить его через `\o /tmp/q01-before.txt`, выполнить запрос и отключить запись командой `\o`. Скопировать файл на компьютер: `docker compose cp postgres:/tmp/q01-before.txt ./q01-before.txt`. Для остальных задач меняйте имя файла.

Для разбора времени отдельных узлов отдельно сохраните план без TIMING OFF. Медиана и структурное изменение важнее одного удачного запуска. Если предпочитаете автоматические замеры:

```sh
python3 tools/measure.py --solutions solutions --runs 3
```

Скрипт прогревает каждый вариант один раз, затем выполняет по три чередующихся измерения с `EXPLAIN (ANALYZE, BUFFERS, SETTINGS, TIMING OFF, FORMAT JSON)`. После этого сохраняет по одному отдельному плану с таймингами узлов. Файлы находятся в results/; сводка — summary.csv. При повторном запуске файлы с теми же именами заменяются: копируйте прежнюю папку results, если хотите сохранить другой эксперимент.

Для каждой задачи укажите:

1. Все три измерения и медиану Execution Time.
2. Общие shared hit/read и temp read/written из корня дерева; Planning отдельно.
3. Строки и loops важного узла, вход сортировки/агрегации, Sort Method или Batches при наличии.
4. Проверку равенства и объяснение, какая работа исчезла.
5. Формулу ускорения `median_before / median_after` и ограничение вывода.

Не нужно получить заданное число миллисекунд или заданный коэффициент. Если выигрыш мал или новая версия хуже, исследуйте причину и зафиксируйте честный результат. Нельзя объяснять ускорение тем, что изменилось только cost.

## 6 Сдать отчёт

- Заполненный queries.sql с исходной и новой версиями пяти запросов. При автоматической проверке также приложите solutions/*.sql.
- Планы до/после всех пяти задач и результаты трёх измерений каждой версии; JSON и папка results/ нужны только при использовании скриптов.
- Заполненный [шаблон отчёта](report-template.md) со всеми пятью сравнениями.
- Результаты comparison.sql или tools/check.py и короткие объяснения по задачам; проверку метаданных колонок приложите отдельно для ручного способа.

Для каждой задачи достаточно 5–8 содержательных предложений: контракт, проблемный узел, объём работы, изменение, проверка смысла, результат измерения и граница применимости. Общие фразы «убрал подзапрос, поэтому быстрее» не объясняют эффект.

Оценка каждой задачи — 20 баллов: сохранение результата и пограничных случаев 6, объяснение плана 5, аргументированное переписывание 4, сравнимые измерения 3, воспроизводимость отчёта 2. Зачёт — от 75/100 при сдаче всех пяти задач и без нарушения контрактов. Несовпадающий результат или использование индекса не засчитываются как оптимизация, даже при хорошей задержке.

## 7 Дополнительные исследования

Выберите одно или два, если хотите глубже проверить границы метода:

1. Q1 для одного клиента: сравните коррелированную и групповую формы при ограничении c.id=1. Почему универсальный совет о подзапросах не работает? Не создавайте индекс.
2. Q2 с другим порогом sku_id: повторите для <=5 и <=95, сохраните смысл пары. Как изменились селективность и выгодный план?
3. Q5 через row_number над событиями уже выбранных заказов: сравните с вариантом DISTINCT ON. Какая часть эффекта принадлежит уменьшению входа?
4. Посчитайте «заказы без успешной оплаты» через NOT EXISTS и через NOT IN. Объясните действие NULL order_id в payments. Не выдавайте эти формы за эквивалентные.
5. В отдельной READ ONLY транзакции выполните `SET LOCAL work_mem='16MB'` для Q3/Q4/Q5 и сравните с 4MB. Запишите это как самостоятельный опыт настройки, не как результат основного переписывания.

Готовые решения и ответы — в [ключе](answer-key.md) и [self-check](self-check/README.md). Открывайте их после самостоятельной попытки. Перед остановкой выйдите из psql через `\q` и выполните `docker compose down`; том с данными сохранится.

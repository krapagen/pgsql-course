# Домашнее задание 2 Внутреннее устройство PostgreSQL

**Ориентировочное время — 60–90 минут** при установленном Docker с Docker Compose либо доступной PostgreSQL. Выполните массовые изменения, сравните число строк и размеры таблицы, объясните результат через MVCC и версии строк.

Все нужные файлы находятся в этой папке. Команды выполняйте из папки с `compose.yaml`. Инструкция подключения — в [README](README.md), готовая схема — [schema.sql](schema.sql), исходные данные — [seed.sql](seed.sql). Свои команды удобно писать в [queries.sql](queries.sql).

## Кейс и условия

Сервис обучения хранит процент прохождения курса. В таблице `homework02.progress` есть `id`, `progress` и служебный текст `payload`. Обновления прогресса и удаление части участников меняют данные; нужно проверить, как это отражается на занятом месте.

- Исходно в таблице 30 000 строк с `progress = 20`.
- Схема и данные готовы; дополнять DDL в этом задании не нужно.
- Autovacuum отключён только для учебной таблицы на время опыта.
- A удерживает исходный снимок REPEATABLE READ, B выполняет изменения отдельно с autocommit.
- После работы завершите A и восстановите настройку autovacuum.

## Шаг 1 Запустить стенд

В папке пакета выполните:

```sh
docker compose up -d --wait
docker compose exec -T postgres psql -X -U course -d course_hw02 -c 'SELECT version(), current_database(), current_user;'
```

Пользователь — `course`, база — `course_hw02`. Отдельный SQL-клиент устанавливать не нужно. Если используете свою PostgreSQL, создайте отдельную пустую базу и выполняйте SQL в привычном клиенте.

## Шаг 2 Применить схему

Готовый `schema.sql` создаёт отдельную учебную таблицу. Примените его один раз к пустой базе:

```sh
docker compose cp schema.sql postgres:/tmp/schema.sql
docker compose exec -T postgres psql -X -U course -d course_hw02 -v ON_ERROR_STOP=1 -f /tmp/schema.sql
```

Для повторного прогона используйте другую пустую базу. Порядок действий есть в README.

## Шаг 3 Загрузить данные

Готовый `seed.sql` примените один раз после создания схемы:

```sh
docker compose cp seed.sql postgres:/tmp/seed.sql
docker compose exec -T postgres psql -X -U course -d course_hw02 -v ON_ERROR_STOP=1 -f /tmp/seed.sql
```

В конце должно быть 30 000 строк; минимальный и максимальный `progress` равны 20. Начальное обслуживание выполняется до открытия снимка A.

## Шаг 4 Снять исходный замер и открыть снимок

Откройте в двух отдельных терминалах интерактивные psql A и B:

```sh
docker compose exec postgres psql -X -U course -d course_hw02
```

В B выполните два готовых SELECT из начала `queries.sql`. Сохраните число строк, размеры в байтах и статистику с пометкой «до изменений». COUNT даёт число видимых строк; `n_live_tup` и `n_dead_tup` являются оценками. Если счётчики запаздывают, повторите чтение через несколько секунд.

Затем в A выполните:

```sql
SET application_name = 'hw02_reader';
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM homework02.progress;
SELECT id, progress, ctid, xmin
FROM homework02.progress WHERE id = 5;
```

Оставьте подключение и транзакцию A открытыми. Первый SELECT устанавливает снимок. Одноразовый запуск через `psql -f` здесь не подходит: после закрытия подключения снимок исчезнет.

## Шаг 5 Написать изменения и сравнить результаты

Самостоятельно напишите и выполните в B три команды:

1. Увеличить `progress` на 1 у всех записей.
2. Ещё раз увеличить `progress` на 1 у всех записей.
3. Удалить строки, для которых `id % 10 < 3`.

Выполняйте команды отдельно с autocommit, без общего BEGIN/COMMIT. После каждой повторите два запроса замеров из `queries.sql`; подпишите этап и сохраните число затронутых строк. В A и B повторите запросы COUNT и чтения `id = 5` из шага 4. Объясните разницу результатов.

Для `heap_bytes` и `total_bytes` отдельно рассчитайте изменение между исходным замером и результатом после DELETE:

```text
разница_байт = размер_после - размер_до
рост_процентов = разница_байт / размер_до × 100%
```

Используйте дробное деление. Сравнивайте одну и ту же функцию размера до и после. Не складывайте heap и размер таблицы: heap уже входит в него. Точных мегабайт и обязательного роста «в N раз» в критериях нет.

### Дополнительно Сравнить две очистки

Пока A открыта, выполните в B `VACUUM (VERBOSE, ANALYZE, TRUNCATE FALSE) homework02.progress;` вне транзакции. Сохраните сообщения, повторите замеры и найдите A в `pg_stat_activity`. Затем выполните COMMIT A и повторите VACUUM и замеры в B. Новый SELECT в A сделайте после второй очистки.

Сравните возможность очистки при открытом и завершённом снимке. `TRUNCATE FALSE` отключает сокращение пустого хвоста файла. Готовый пример и пояснения находятся в ключе. VACUUM FULL, настройка реплики и искусственный crash не входят в работу.

## Шаг 6 Объяснить результат и завершить работу

Напишите 5–8 предложений: как изменилось число логических строк; откуда появились физические версии; зачем сохранялись данные для A; что означает dead tuple; какую работу выполняет обслуживание и почему размер файла не обязан сразу уменьшиться.

Если A ещё открыта, выполните в ней `COMMIT;`. Проверьте новыми SELECT её видимость. В B восстановите настройку таблицы:

```sql
ALTER TABLE homework02.progress RESET (autovacuum_enabled);
SHOW autovacuum;
SELECT reloptions FROM pg_class
WHERE oid = 'homework02.progress'::regclass;
```

На готовом стенде autovacuum включён, а в `reloptions` больше нет `autovacuum_enabled=false`. После выхода из обоих psql через `\q` остановите стенд командой `docker compose down`.

Сдайте `queries.sql` и короткий отчёт: версия PostgreSQL, условия опыта, числа затронутых строк, замеры по этапам, расчёт роста и объяснение. Для дополнительной части приложите диагностику A и сообщения обеих очисток. Укажите отклонения от последовательности и подтвердите завершение A и восстановление настройки.

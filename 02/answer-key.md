# Ключ к домашнему заданию второго занятия

## Внутреннее устройство PostgreSQL

Откройте ключ после самостоятельного выполнения. Сопоставьте свои команды, замеры и объяснение с примерами ниже. SQL может быть оформлен по-другому; точные размеры, физические адреса и время обновления статистики зависят от прогона.

## 1 Готовая схема

```sql
-- Домашнее задание 2. Готовая схема; выполнить один раз в пустой базе.
-- На время опыта автоматическая очистка отключена только у этой таблицы.
BEGIN;

CREATE SCHEMA homework02;

CREATE TABLE homework02.progress (
    id bigint PRIMARY KEY,
    progress integer NOT NULL CHECK (progress BETWEEN 0 AND 100),
    payload text NOT NULL
) WITH (fillfactor = 100, autovacuum_enabled = false);

COMMIT;
```

`id` идентифицирует логическую запись. `progress` хранит процент прохождения, `payload` задаёт небольшой объём данных в строке. Fillfactor равен 100; autovacuum временно отключён только у этой таблицы. В конце задания настройка возвращается к значению по умолчанию.

## 2 Исходные данные

После готового seed в таблице должны быть 30 000 строк с progress 20. `payload` состоит из восьми повторений md5 от ID и имеет длину 256 символов. Начальный VACUUM ANALYZE выполняется до открытия снимка A.

```sql
SELECT count(*) AS logical_rows, min(progress), max(progress)
FROM homework02.progress;
```

Результат — 30 000, 20, 20. Для повторного опыта создайте другую пустую базу, примените схему и seed заново.

## 3 Решения запросов и массовых изменений

### Замеры

В B с autocommit выполняйте на каждом этапе:

```sql
SELECT
    (SELECT count(*) FROM homework02.progress) AS logical_rows,
    pg_relation_size('homework02.progress'::regclass) AS heap_bytes,
    pg_table_size('homework02.progress'::regclass) AS table_bytes,
    pg_indexes_size('homework02.progress'::regclass) AS index_bytes,
    pg_total_relation_size('homework02.progress'::regclass) AS total_bytes;

SELECT n_live_tup, n_dead_tup, n_tup_upd, n_tup_del,
       last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE schemaname = 'homework02' AND relname = 'progress';
```

COUNT даёт точное число видимых строк. Heap — основной файл таблицы; table_bytes включает её вспомогательное хранение, а total_bytes также включает индексы. По функциям размера `total_bytes = table_bytes + index_bytes`; добавлять heap повторно нельзя.

`n_live_tup` и `n_dead_tup` являются оценками. Счётчики операций могут обновляться с задержкой. Перечитайте статистику через несколько секунд с autocommit. `pg_stat_clear_snapshot()` сбрасывает локальный кэш, а не заставляет другой backend немедленно публиковать данные.

### Два UPDATE и DELETE

Пока A удерживает исходный снимок, в B выполните команды отдельно:

```sql
UPDATE homework02.progress SET progress = progress + 1;
UPDATE homework02.progress SET progress = progress + 1;
DELETE FROM homework02.progress WHERE id % 10 < 3;
```

Снимайте замеры после каждой команды. На свежих данных ожидаются следующие результаты:

| Этап | Результат команды | COUNT в B | progress у id = 5 |
| --- | --- | ---: | ---: |
| До изменений | — | 30 000 | 20 |
| Первый UPDATE | UPDATE 30000 | 30 000 | 21 |
| Второй UPDATE | UPDATE 30000 | 30 000 | 22 |
| DELETE | DELETE 9000 | 21 000 | 22 |

Условие удаления выбирает 30% исходных строк. `id = 5` остаётся в таблице. Повторный запуск изменений поверх результата не воспроизводит исходный опыт.

Готовое решение с замерами находится в [self-check/queries.sql](self-check/queries.sql). Оно выполняется в B после открытия снимка A по [порядку самопроверки](self-check/README.md).

### Расчёт роста

Для каждой метрики отдельно используйте пару «до изменений / после DELETE». Например, если heap вырос с 9 109 504 до 27 312 128 байт:

```text
разница = 27 312 128 - 9 109 504 = 18 202 624 байта
рост = 18 202 624 / 9 109 504 × 100% ≈ 199,82%
```

Итоговый размер примерно в 3 раза больше исходного; прирост составляет примерно 200%. Для total_bytes используйте собственные значения. Байты из примера не являются требованием для зачёта.

## 4 Снимок и дополнительная очистка

### Что читает A

До изменений B в интерактивном psql A:

```sql
SET application_name = 'hw02_reader';
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM homework02.progress;
SELECT id, progress, ctid, xmin
FROM homework02.progress WHERE id = 5;
```

Первый SELECT устанавливает снимок. A остаётся подключённой и продолжает видеть 30 000 строк и progress 20 после завершённых изменений B. Новый SELECT B видит 21 000 и 22. У новой версии id 5 другой ctid; логический ID не меняется.

После COMMIT самой A следующий SELECT получает новый снимок и видит 21 000 и 22. Если выполняете дополнительную часть, отложите это чтение до второй очистки B, чтобы не менять порядок наблюдений.

### Первая очистка при открытой A

В B вне BEGIN/COMMIT:

```sql
SELECT pid, application_name, state,
       clock_timestamp() - xact_start AS xact_age, backend_xmin
FROM pg_stat_activity
WHERE datname = current_database()
  AND application_name = 'hw02_reader';

VACUUM (VERBOSE, ANALYZE, TRUNCATE FALSE) homework02.progress;
```

Найдите A в состоянии `idle in transaction` с backend_xmin. Она ждёт следующей команды клиента, сохраняя снимок. В сообщениях очистки ищите `dead but not yet removable`: версии, нужные старому снимку, пока сохраняются. Повторите замеры.

### Вторая очистка после завершения A

В A выполните `COMMIT;`. Затем повторите в B тот же VACUUM и замеры. Ненужные версии могут быть убраны; COUNT в B остаётся 21 000. При TRUNCATE FALSE размер heap сохраняется, хотя место внутри файла становится доступно для новых версий. Общий размер с индексами также не обязан уменьшаться.

Готовый файл [self-check/vacuum.sql](self-check/vacuum.sql) объединяет диагностику и очистку. Запустите его сначала при открытой A, затем после её COMMIT. После второй очистки повторите чтение A. Не требуйте фиксированного числа removed: промежуточные операции могут изменить объём работы, оставшийся самому VACUUM.

## 5 Объяснения и завершение

### Строка и физические версии

UPDATE создаёт новую физическую версию логической строки. DELETE прекращает видимость записи для новых снимков, но её прежняя версия может сохраняться для старого читателя. Поэтому уменьшение COUNT не означает немедленного уменьшения файла. Снимок задаёт правила выбора видимых версий, а не создаёт отдельную полную копию таблицы.

Dead tuples связаны с устаревшими или удалёнными версиями. Невидимость конкретному SELECT ещё не гарантирует возможность немедленного удаления. `n_dead_tup` не является точным счётчиком занятых или свободных байтов.

### Назначение обслуживания

Обычный VACUUM возвращает место для повторного использования внутри таблицы; в общем случае он не обязан уменьшать файл. TRUNCATE FALSE дополнительно отключает сокращение пустого хвоста. ANALYZE собирает статистику для планировщика. VACUUM FULL переписывает таблицу с сильной блокировкой и не входит в задание.

### Восстановление настройки

После COMMIT A в B:

```sql
ALTER TABLE homework02.progress RESET (autovacuum_enabled);
SHOW autovacuum;
SELECT reloptions FROM pg_class
WHERE oid = 'homework02.progress'::regclass;
```

В готовом стенде SHOW показывает on; из настроек таблицы удалено autovacuum_enabled=false, fillfactor=100 остаётся. Если использовали собственную PostgreSQL с другими глобальными настройками, укажите это в отчёте.

### Пример короткого объяснения

После двух UPDATE число логических строк в B оставалось 30 000, а после DELETE стало 21 000. При этом измеренный heap вырос: для изменённых записей появились новые физические версии. A читала исходные данные по старому снимку, поэтому нужные ей версии сохранялись. После завершения A очистка смогла убрать ненужные версии. При TRUNCATE FALSE свободное место осталось внутри файла, а размер heap сохранился. Оценку n_dead_tup нужно сопоставлять с сообщениями VACUUM и замерами, учитывая задержку статистики.

Если дополнительную часть не выполняли, не описывайте её как собственное наблюдение. Для основной части нужны SQL двух UPDATE и DELETE, сравнимые замеры, расчёт изменения размеров и объяснение через MVCC. Точные мегабайты, адреса ctid и обязательный коэффициент роста не фиксированы.

Если A показывает новые данные сразу, проверьте REPEATABLE READ, момент первого SELECT и сохранение подключения. Если VACUUM сообщает об ошибке транзакционного блока, выполняйте его отдельно вне BEGIN/COMMIT.
